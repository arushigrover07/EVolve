## Q1(a): EV charging peak and scaled architecture - 1 mark

### Domain scenario and busiest API

A holiday departure rush near a campus and adjoining highway can cause many EV
drivers to search for stations and available chargers at the same time. EVolve's
actual station-list UI fetches **GET /api/stations**. In `backend/app.js`, that route
joins stations to chargers and aggregates total, available and charging counts,
ordered by station ID. It is a realistic shared read path during this rush.
It performs a SELECT; it does not create bookings, start/complete charging sessions
or write telemetry. The intended benchmark uses no POST, PUT or DELETE API.

### Actual local setup

`frontend` serves the React build and runs the single Nginx load balancer on
container port 80, published at host **5173**. `backend1`, `backend2`, `backend3`
listen on internal **5000**, with no published API host ports. They share the
`evolve_default` Docker network. The actual Nginx upstream includes all three
service DNS names. The default policy is round-robin; observed counts need not be
perfectly equal. `/api/` retains paths/query strings/methods/bodies; `/health` is
process liveness and does not prove database readiness.

Compose's explicit `VITE_API_URL=/` maps to same-origin `/api/...` requests. Outside
Compose, the existing explicit API setting and empty/unset local/Render fallbacks
are retained. This local scaling experiment is **not deployed on Render**.

Each API pool is capped at 5 connections: **15 maximum across three replicas**,
excluding existing hosting/admin clients. Pools are lazy. No telemetry worker is
running locally; API startup never starts one. The optional worker would add up
to 5 connections but was not enabled. Startup schema alteration was previously
extracted into an explicit migration; no migration was executed here.

The three APIs currently have identical filesystem layers and different image IDs
because image metadata includes per-service labels. A single-ID alignment override
and exact rollback snapshot are prepared and model-validated, but were not applied
because the station API is not ready. Source Git revision is not attested by OCI
labels; uncommitted working-tree changes are not described as a deployed commit.

## Q1(b): One backend versus three - 1.5 marks

### Controlled protocol

Use the existing k6 tooling, now verified with native **k6.exe v1.8.2 (commit/682f083071, go1.26.9, windows/amd64)**.
The official Windows archive checksum matched its published checksum; the portable
binary is under ignored `.local-tools/`, without system installation.
Native `k6 inspect` initialized both workloads. A separate **20-request /health
functional smoke** completed without failures and confirmed resolved workload
gauges. It is not a station benchmark and its RPS/latency is not used here.

The intended paired runs use exactly 1000 measured client requests, 20 VUs,
GET /api/stations, 20-second timeout, identical headers/tool/binary/settings,
no redirects, no scripted retries and zero warm-up requests. One uses an isolated
proxy at 127.0.0.1:5174 forwarding to existing backend1; Three uses 127.0.0.1:5173.
Both include equivalent Nginx settings, with retries disabled. No extra backend,
pool or worker is created for the baseline. It uses a separate project and an
approved immutable frontend image; cleanup targets only its verified full ID.

Unmeasured read-only response snapshots bracket each measured run. Hashes must
match within and across runs. These detect observed data changes, not all possible
transient changes. Snapshot requests are excluded from the 1000 measured requests.
The runner records raw summary, separate process metadata/exit code, actual
resolved gauges, artifact hashes, tool/image identities and explicit acceptance.
The comparator independently verifies fields, raw counts, named HTTP-200 checks,
thresholds and file contents. Failed, incomplete or incompatible runs are rejected.

Client HTTP counts, backend attempts and SQL statements are distinct. Backend and
SQL counts are unmeasured; 1000 client requests do not prove 1000 SQL executions.

## Q1(c): Failure handling - 1.5 marks

### Implemented experiment and retry policy

The isolated before config is `benchmarks/nginx.failover-before.conf`, matching
no-retry three-instance benchmarking. The after config adds a shared upstream zone,
`max_fails=1 fail_timeout=30s`, connect timeout 1s, and bounded retries on the exact
read endpoint: error/timeout/502/503/504, at most three upstream attempts and a
5-second retry window. Non-idempotent retries are not enabled. That temporary
benchmark location admits GET/HEAD only; ordinary application Nginx is unchanged.
Read/send timeouts remain inactivity timeouts, not a guarantee of zero failures.

The same k6 failure workload uses 1000 requests, 20 VUs, 20-second request timeout
and 0.5s pacing per iteration in both phases, ensuring a sufficiently long run.
The controller waits at least 8 seconds from the first request and for observed
in-flight activity, validates the exact owned backend3 ID/image, then requests a
15-second graceful stop. It refuses unrelated load tools or unexpected traffic.
It logs request starts/ends, stop requested/completed timestamps and restoration.
It restores only the same verified backend ID and waits for liveness. Validation
requires complete matching logs/raw metrics, a stop overlapping real requests,
identical workload metadata, stable observed data and successful recovery.

Failure categories are disjoint: timeouts; other transport failures; HTTP non-2xx.
Total failed clients = their sum. Retrying a GET may repeat backend/database work,
so client success alone is not proof of one upstream execution. Retries are bounded
and isolated to avoid silently changing ordinary application behavior.

blocks a meaningful failover experiment. Native Nginx syntax checks and offline

## Q1(d): Actual architecture and proposed edge extension - 1 mark

![Actual local setup, separate hosted references and proposed edge gateway](architecture/evolve-q1.png)

Editable sources: [Mermaid](architecture/evolve-q1.mmd),
[SVG](architecture/evolve-q1.svg), [shared layout renderer](../../../scripts/render-q1-architecture.py).
The PNG and SVG were generated from one layout and visually inspected. Actual
local names/ports are shown. Neon is provider-confirmed without recording its URL.
Render is identified by the existing frontend API configuration/project history;
its live services and process port were not inspected or changed. Grey hosted
connections are project references, not claims of a verified live connection.

The **purple proposed EV charging-site edge gateway** caches recent availability
with an explicit short TTL (for example 5 seconds), shows freshness/staleness, and
buffers telemetry during unreliable connectivity. During a holiday rush, repeated
nearby availability lookups can be served locally, reducing unnecessary WAN reads
and response delay. After recovery, timestamped/sequence-labelled telemetry must
reach the central API for reconciliation and durable storage. Authoritative
bookings, user/account changes and final session/billing records remain central;
a stale cache must not authorize conflicting reservations. This is a proposal,
not implemented hardware or an existing offline-booking capability. EVolve's
current telemetry is simulated. Edge/fog is chosen because charging sites can
experience intermittent network connectivity; it complements, rather than replaces,
central consistency and cloud API capacity.

## Validation, evidence and limitations

See [evidence/verification/results.json](evidence/verification/results.json) and
logs for exact executed commands and timestamps. Backend suite, frontend API-routing
tests, production build, benchmark/recovery tests, syntax and Compose models passed.
Latest source-dependent checks are recorded in `verification/final-delta.json`.
The existing frontend lint check **failed** with 15 errors and 2 warnings; these
pre-existing unused-variable/effect issues were not silently fixed or called passed.
No complete browser end-to-end regression suite exists. Native Nginx checks passed
for ordinary and all four benchmark/failure configs; an initial stdin validation
method failed because the input was not read as a regular config file. That failed
attempt is preserved separately; unique temporary wrapper files validated correctly
and were removed without reloading the running configuration.

Readiness probes are not benchmarks. The local stack's process liveness is healthy,
but a configured Neon read connection fails with ETIMEDOUT despite DNS resolution.
The underlying network/provider cause is not proven. TLS verification was not
disabled, credentials were not inspected, and no schema/data repair was attempted.
The blocking dependency is restoring authorized read connectivity from the local
Docker application to its existing cloud database. Until then, Q1(a) cloud-data
behavior and Q1(b)/(c) runtime demonstrations remain incomplete.

No application containers/images/networks/volumes were changed. Only the native
Nginx test process used uniquely named temporary files, removed afterward. No
migration, application data write, Render deployment/configuration change, commit
or push occurred. Q2 was not started. GitHub branch reference: https://github.com/arushigrover07/EVolve/tree/da3
(local work is uncommitted; remote branch contents were not verified or updated).
Manual genuine screenshots and a three-minute demo checklist are in
[screenshots-and-demo.md](screenshots-and-demo.md).
